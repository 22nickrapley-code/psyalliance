# Use these as living acceptance records

- `functional_parity.csv`: required product behaviours and source anchors; target results start Pending.
- `demo_scenarios.csv`: required coherent fictional journeys; all target/demo results start Pending.
- `demo_route_inventory.csv`: discovery categories to expand into one row per actual original demo entry point. Categories are not claims about existing routes.
- `backend_mapping.csv`: actual original-service/API/schema mapping to complete before implementing adapters.
- `visual_capture_plan.csv`: paired reference/target states and viewports; add every discovered demo variant.
- `implementation_exceptions.csv`: record proposed/approved deviations, especially any visible change.
- `source_inventory.json`: automatically extracted source functions, modal kinds, form IDs, action-handler kinds, stylesheet/script order and initial fixture summary. Internal/legacy handlers do not automatically imply visible UI requirements.
- `reference_test_results.txt`: actual reference regression run when this package was assembled, not target/backend evidence.

All 'Pending' target results must be resolved with evidence. Do not replace this with a prose claim of parity. Keep evidence in the original repository or its controlled review storage; do not place real client data in screenshots or fixtures.
